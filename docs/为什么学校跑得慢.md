# py++ 在学校跑 4400ms 的原因分析

> 结论先行：**4400ms 不是 py++ 的常规性能，而是「冷启动 + 缺缓存 + 慢磁盘」的叠加结果。**
> 同一份代码在本机冷编译 272ms、命中缓存 31ms，云端接口 160~260ms。

---

## 一、实测数据（先看数，别猜）

| 情形 | 本机实测 | 学校（推断 + 可自测） |
|---|---|---|
| 云端 `/api/cpy/run` | **160~260ms** | — |
| 命中缓存（热跑） | **31ms** | 若第二次仍慢 → 缓存没生效 |
| 冷编译（`PYPP_NO_CACHE=1`） | **272ms**（gcc 编译 165ms） | ⬅ **主要嫌疑**，慢盘会放大数倍 |
| 纯 VM 降级跑小循环 | **109ms** | 小代码不慢；大循环才慢 |
| import + find_gcc | **49ms**（29 + 20） | 无 `__pycache__` 时可到几百 ms |
| **学校整轮实测** | — | **4400ms** |

比例参考（源码注释里记的，来自开发机）：完整编译 ~437ms → 命中缓存 ~130ms。

---

## 二、为什么学校会慢 16 倍

py++ 每次运行都**新起一个 Python 进程**，走这条流水线：

```
python 启动 → import 各模块 → find_gcc 探测工具链
   → 词法/语法/修复/代码生成 → 调 gcc 编译 → 执行 → 打印
```

4400ms 由这几项叠加而成：

### 1. 每次都冷编译（最主要）
学校的机器上**没有 `~/.pypp/cache` 命中**，或者压根没跑过第二次。
- 冷编译要真调一次 gcc，**编译 165ms 只是本机 SSD 的成绩**
- 学校多为**机械硬盘 / 网络盘 / 带杀软实时扫描**的机房机 ——
  gcc 启动 + 读大量头文件 + 写临时 exe，磁盘 I/O 会被放大数倍
- 机房机常见的**杀软实时防护**会对新建 .exe 做扫描，进一步拖慢

### 2. Python 进程冷启动
- 本机 import 只要 29ms（盘快、有 `__pycache__`）
- 学校机器首次 import 要**从 .py 源码编译字节码**（无 `__pycache__` 或被杀软拦）
  这一步能到 **几百 ms~1s+**
- Python 本体在机械盘上的冷启动本身就比 SSD 慢很多

### 3. 工具链探测（find_gcc）
- 本机 20ms（命中自带便携工具链）
- 学校若无自带工具链，会去**逐个试 `C:\mingw64`、`C:\msys64`、PATH** 等位置，
  每次 `subprocess` 探测都有进程创建开销 —— **且探测结果只在单进程内缓存**，
  下次运行**重新探测**

### 4. 可能的降级路径（视程序而定）
若学校机器**完全没有 gcc**，py++ 会降级到**内置 VM 解释执行**。
- **实测**：VM 跑 `s=0; for i in range(100000): s+=i` 只要 **109ms** ——
  说明 VM 对小段代码**并不慢**，**不能一上来就赖 VM**。
- 但 VM 是**纯 Python 逐条解释**，对**循环/计算密集**程序会随规模线性放大；
  若学校跑的是重循环程序，VM 路径确实可能到秒级。
- 所以：**「是不是 VM」要用横幅 + 程序类型一起判断**，不能只看耗时。

## 三、判断学校到底卡在哪（三步定位）

让学生/你在学校机器上执行：

```bat
:: 1) 看有没有 gcc（有 → native，无 → VM 慢路）
where gcc
python -c "import sys;sys.path.insert(0,r'<py++目录>\src');from pypp import find_gcc;print(find_gcc())"

:: 2) 看是否是冷编译（连跑两次对比）
::    第一次跑，记下耗时；紧接着再跑一次同样的代码
::    若第二次明显变快 → 就是冷编译/缓存问题

:: 3) 单独测 gcc 编译本身
gcc --version
::    以及看 py++ 输出横幅里的「引擎: 原生高速模式」还是「内置 VM 模式」
```

判据：
| 现象 | 结论 |
|---|---|
| 第一次慢、第二次快 | **冷编译问题**（缓存没命中/被清） |
| 两次都慢，且横幅写「内置 VM 模式」 | **没有 gcc**，在跑解释器 |
| `gcc --version` 本身就要好几秒 | **磁盘/杀软问题**，不是 py++ 的锅 |

## 四、可落地的优化（按性价比排序）

### 对用户侧（学校机器）
1. **确认使用「便携版」**：`tools/mingw64` 里自带 gcc，
   避免走 PATH 探测、也避免无 gcc 降级到 VM
2. **关掉该目录的杀软实时扫描**（机房机常见，效果立竿见影）
3. **预热**：第一次慢是正常的，第二次会命中缓存

### 对 py++ 本身（代码层）
| 优化 | 收益 | 成本 |
|---|---|---|
| **把 `find_gcc` 结果落盘缓存**（现在只进程内缓存，每次重探） | 省 20ms~1s | 小 |
| **`__pycache__` 随包分发**（预编译 .pyc，省首启字节码编译） | 省几百 ms | 小 |
| **启动横幅加「本次是否冷编译」提示** | 帮用户分辨冷/热 | 小 |
| **缓存预热脚本**（首次安装后自动跑一次 hello） | 消灭首启慢 | 小 |
| **提供常驻服务模式**（避免每次新起 Python 进程） | 省整段启动开销 | 中 |
| **VM 路径优化或用更快的解释策略** | 无 gcc 时救命 | 大 |

---

## 五、一句话回答「为啥 4400ms」

> **因为那是「第一次跑、且机器慢」的成绩** —— 冷编译要真调 gcc，
> gcc 启动 + 读头文件 + 写 exe 在机械盘/带杀软的机房机上会被放大十几倍；
> 若机器还没装 gcc，则是在跑纯 Python 的 VM 解释器，更慢。
> 同一份代码在本机只要 272ms（冷）→ 31ms（热）。
> **先确认学校机器有没有 gcc、第二次跑是否变快**，就能定位到具体是哪一条。
